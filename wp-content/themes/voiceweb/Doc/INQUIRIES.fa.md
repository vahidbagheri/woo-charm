# خرید معمولی و درخواست تماس

[راهنمای ووکامرس](./WOOCOMMERCE.fa.md) · [تحویل پروژه](./HANDOFF.fa.md)

این قابلیت بخشی از قالب `voiceweb` است. برای محصولی که نیاز به مشاوره یا هماهنگی فروش
دارد، مشتری مدل محصول و شمارهٔ موبایل را ثبت می‌کند و فروشگاه بعداً تماس می‌گیرد.
درخواست تماس **سفارش مالی، پرداخت، فاکتور یا رزرو موجودی نیست** و هیچ پیامک یا ایمیل
خودکاری ارسال نمی‌کند. شمارهٔ این فرم با OTP تأیید نمی‌شود؛ مدیر هنگام تماس اعتبار آن را
بررسی می‌کند. ورود و ثبت‌نام پیامکی همچنان مسئولیت افزونهٔ مستقل VoiceWeb Auth است.

## تنظیمات فروشگاه و محصول

در **ووکامرس ← پیکربندی ← محصولات ← همگانی**، بخش «درخواست تماس ویس وب» قرار دارد.
گزینهٔ `voiceweb_wc_purchase_mode` دو مقدار دارد:

| مقدار | رفتار |
|---|---|
| `purchase` | خرید، سبد و پرداخت معمولی ووکامرس؛ حالت پیش‌فرض |
| `inquiry` | ثبت شماره و پیگیری فروشگاه برای محصولات ساده و متغیر |

در ویرایش محصول، **اطلاعات محصول ← همگانی ← روش خرید ویس وب** می‌توان «پیش‌فرض فروشگاه»،
«خرید و پرداخت» یا «درخواست تماس» را انتخاب کرد. مقدار متای `_voiceweb_purchase_mode`
خالی، `purchase` یا `inquiry` است. گزینهٔ صریح محصول از تنظیم سراسری جلوتر است.
تمام variationها روش خرید والد را به ارث می‌برند؛ override مستقل variation تعریف نشده است.
محصول خارجی و گروه‌بندی‌شده مسیر بومی خود را حفظ می‌کنند؛ این ماژول برای ساده و متغیر است.

تنظیم سراسری از ابتدا `purchase` است. نمونهٔ محتوایی درخواست تماس می‌تواند فقط در متای
همان محصول `inquiry` باشد. تغییر روش خرید، سفارش‌های قبلی یا وضعیت مالی آن‌ها را تغییر نمی‌دهد.

## مسیر کاربر

محصول ساده در صفحهٔ محصول یا کارت کاتالوگ دکمهٔ «درخواست تماس» دارد. محصول متغیر از کارت
به صفحهٔ محصول می‌رود تا کاربر ابتدا گزینه‌های موجود را انتخاب کند.
فرم `variations_form` و اسکریپت بومی ووکامرس باقی می‌مانند؛ افزونهٔ
`woo-variation-swatches` همان selectهای بومی را به swatch تبدیل می‌کند.
فقط دکمهٔ خرید variation با دکمهٔ تماس جایگزین می‌شود. وقتی گزینه‌ها خالی یا ناموجودند،
دکمه غیرفعال است؛ رویدادهای `found_variation`، `reset_data` و `hide_variation` وضعیت آن را
به‌روز می‌کنند. هیچ موتور دوم برای تطبیق variation نوشته نشده است.

مودال `dialog` شامل نام محصول/مدل، موبایل الزامی، نام اختیاری، توضیح اختیاری و رضایت الزامی
برای تماس است. حد نام ۱۲۰ و توضیح ۱۰۰۰ کاراکتر است. اعداد فارسی/عربی، فاصله‌ها و شکل
بین‌المللی ایران `+98`، `0098` و `98` در سرور به `09xxxxxxxxx` تبدیل می‌شوند.
شمارهٔ ثابت پذیرفته نمی‌شود. فرم بزرگ‌تر از ۸ کیلوبایت رد می‌شود.

کیبورد موبایل برای تلفن است و `autocomplete="tel"`/`name` فعال است. `dialog.showModal()`
پس‌زمینه را غیرفعال و فوکوس را داخل مودال نگه می‌دارد. بستن با دکمه، Escape یا بیرون مودال
ممکن است و فوکوس به دکمهٔ آغاز برمی‌گردد. هنگام ارسال، بستن و ارسال مجدد موقتاً غیرفعال است؛
خطای شبکه داخل فرم نمایش داده می‌شود و دادهٔ نوشته‌شده باقی می‌ماند. درخواست شبکه بعد از
۲۰ ثانیه timeout دارد. بعد از موفقیت، پیام تأیید نمایش داده و فیلدها مخفی می‌شوند.
هدف لمسی حداقل ۴۴ پیکسل و فونت ورودی ۱۶ پیکسل است تا iOS روی فرم زوم ناخواسته نکند.

مودال به JavaScript و مرورگری با native `dialog` نیاز دارد؛ لینک کاتالوگ محصول متغیر بدون
JavaScript همچنان به صفحهٔ محصول می‌رود، اما ثبت درخواست بدون JavaScript پیاده نشده است.

## جلوگیری از خرید ناخواسته

| لایه | کنترل |
|---|---|
| کارت محصول | `woocommerce_loop_add_to_cart_link` دکمهٔ تماس می‌دهد |
| صفحهٔ محصول | دکمهٔ خرید ساده/متغیر با تماس جایگزین می‌شود؛ فرم انتخاب متغیر حفظ می‌شود |
| POST کلاسیک | `woocommerce_add_to_cart_validation` محصول inquiry را رد می‌کند |
| Store API | `woocommerce_store_api_validate_add_to_cart` درخواست افزودن را رد می‌کند |
| سبدی که قبلاً ساخته شده | `woocommerce_check_cart_items` و `woocommerce_store_api_cart_errors` پرداخت محصولی را که حالتش تغییر کرده مسدود می‌کنند |

کاربر محصول inquiry باقی‌مانده در سبد را حذف و از صفحهٔ محصول درخواست تماس می‌دهد.
محصولات عادی همان سبد همچنان قابل خریدند. خودکار محصولی حذف نمی‌شود.
پرداخت سفارش از قبل ساخته‌شده در `/checkout/order-pay/{id}` و سفارش‌های پرداخت‌شده،
پردازش، موجودی و گزارش‌های ووکامرس تحت تأثیر قرار نمی‌گیرند.

سرور دوباره وضعیت انتشار، نوع محصول، نمایش‌پذیری، موجودی و inquiry بودن محصول را بررسی
می‌کند. برای محصول متغیر، variation باید منتشرشده، فعال، دارای قیمت/نمایش بومی، موجود و متعلق
به همان والد باشد. ID انتخابی کاربر به‌تنهایی مجوز دسترسی یا ثبت محصول پنهان نمی‌دهد.
تغییر موجودی/حالت محصول در فاصلهٔ باز کردن فرم تا ارسال نیز در سرور بررسی می‌شود.

## امنیت فرم و API

فقط دو مسیر POST عمومی وجود دارد:

| مسیر | کارکرد |
|---|---|
| `/wp-json/voiceweb/v1/inquiries/session` | آغاز نشست هم‌مبدأ فرم |
| `/wp-json/voiceweb/v1/inquiries` | ثبت درخواست دارای نشست و proof معتبر |

bootstrap فقط `Origin` یا `Referer` دقیقاً مطابق scheme، host و port سایت را می‌پذیرد.
کوکی `vw_inquiry_device` شامل ۳۲ بایت تصادفی hex است؛ ۳۰ روز اعتبار، `HttpOnly`،
`SameSite=Lax` و روی HTTPS ویژگی `Secure` دارد. CSRF از HMAC روی کوکی، کلید خصوصی
WordPress و بازهٔ ساعتی ساخته می‌شود. هدر `X-VW-Inquiry-CSRF` برای بازهٔ فعلی یا قبلی لازم
است؛ nonce عمومی مهمان به‌تنهایی مبنای امنیت نیست. مشتری واردشده علاوه بر آن `X-WP-Nonce`
برای احراز هویت cookie در REST دارد. هیچ موبایل/نام مشتری در تنظیم عمومی اسکریپت ارسال نمی‌شود.

proof شروع فرم نیز HMAC دستگاه و زمان است؛ فرم سریع‌تر از ۲ ثانیه یا قدیمی‌تر از ۳۰ دقیقه
رد می‌شود. client بعد از آماده‌سازی نشست حداقل ۲٫۲ ثانیه صبر می‌کند. فیلد honeypot باید خالی
باشد و رضایت باید boolean `true` باشد. پاسخ API `no-store, private` و `Vary: Cookie, Origin`
دارد. مسیر GET یا لیست عمومی درخواست‌ها وجود ندارد؛ موفقیت فقط پیام و UUID پیگیری می‌دهد.

محدودیت‌های پایدار در دیتابیس با `INSERT IGNORE` و `UPDATE ... WHERE hits < max` اعمال
می‌شوند؛ رقابت همزمان، سقف شمارنده را دور نمی‌زند. reset فاصلهٔ ارسال نیز conditional است:

| مبنا | سقف |
|---|---|
| IP | ۲۰ ثبت در ساعت |
| دستگاه | ۱۰ ثبت در ساعت |
| موبایل | ۱۰ ثبت در روز |
| فاصلهٔ ثبت همان موبایل | حداقل ۶۰ ثانیه |

سقف ساعت/روز بازهٔ ثابت دارد؛ فاصلهٔ ۶۰ ثانیه مستقل از مرز بازه است. در صورت رسیدن به سقف،
پاسخ `429` می‌آید. IP خام ذخیره نمی‌شود؛ کلیدهای شمارنده HMAC هستند.
به هدرهای proxy اعتماد نشده و IP از `REMOTE_ADDR` می‌آید. در پشت reverse proxy معتبر،
هوک `voiceweb/inquiries/client-ip` می‌تواند resolver مورد اعتماد ارائه دهد.
این کنترل‌ها جایگزین rate limit لبهٔ شبکه برای حملهٔ حجیم نیستند.

## داده‌ها و پیگیری کارکنان

دو جدول با prefix واقعی WordPress ساخته می‌شود؛ این نصب ممکن است `wp_` یا prefix دیگری داشته باشد:

| جدول | اطلاعات |
|---|---|
| `{prefix}voiceweb_inquiries` | UUID، account ID اختیاری، محصول/variation، snapshot عنوان/SKU/گزینه‌ها/قیمت/پول هنگام ثبت، موبایل، نام/توضیح، وضعیت، یادداشت داخلی، revision، reviewer، زمان UTC |
| `{prefix}voiceweb_inquiry_limits` | HMAC کلید، bucket، hits و expires؛ بدون موبایل یا IP خام |

نسخهٔ schema در `voiceweb_inquiries_version=1` است. نصب در `init` یک‌بار انجام می‌شود و
درخواست‌های ثبت، سفارش/جدول مالی Woo را نمی‌نویسند. قیمت snapshot برای پیگیری است؛ قبل از
هماهنگی باید قیمت/موجودی فعلی بررسی شود. با تغییر یا حذف محصول، snapshot درخواست باقی می‌ماند.

در **ووکامرس ← درخواست‌های تماس** کاربران دارای `manage_woocommerce` به صف خصوصی دسترسی
دارند. وضعیت‌ها «جدید»، «تماس گرفته شده» و «بسته شده» هستند؛ فیلتر و صفحه‌بندی ۲۰تایی دارد.
کارمند می‌تواند یادداشت داخلی حداکثر ۲۰۰۰ کاراکتر، وضعیت و حذف دائمی درخواست را ثبت کند.
هر write، capability و nonce وابسته به ID می‌خواهد. revision در شرط UPDATE/DELETE قرار دارد؛
ویرایش همزمان یا حذف‌شده پاسخ `409` می‌گیرد و آخرین یادداشت بی‌خبر overwrite نمی‌شود.
مقادیر مشتری در صف escape شده و textarea/لینک تلفن امن خروجی می‌گیرند.
آخرین reviewer و زمان پیگیری ثبت می‌شوند؛ تاریخچهٔ تمام ویرایش‌های گذشته جداگانه ذخیره نمی‌شود.

موبایل‌ها فقط در این صفحهٔ کارکنان و دیتابیس خصوصی هستند؛ سفارش، حساب و کاتالوگ endpoint
برای خواندن آن‌ها ندارند. بانک اطلاعاتی این جدول PII دارد و باید همراه داده‌های خصوصی سایت
backup/دسترسی محدود داشته باشد. حذف حساب، `user_id` درخواست را صفر می‌کند؛ متن و شماره برای
پیگیری فروشگاه باقی می‌ماند. مدیر با دکمهٔ حذف می‌تواند همان درخواست را به‌طور دائمی پاک کند.
export/eraser خودکار WordPress برای مهمان بدون ایمیل/احراز هویت این نسخه تعریف نشده است.
از ذخیرهٔ اطلاعات حساس بانکی در توضیح یا یادداشت داخلی پرهیز شود.

Cron روزانهٔ `voiceweb_inquiry_cleanup` فقط شمارنده‌های منقضی را در batch حداکثر ۱۰هزار حذف
می‌کند؛ درخواست‌ها خودکار حذف نمی‌شوند. غیرفعال شدن/تعویض قالب داده‌ها را حذف نمی‌کند.

## فایل‌ها و قرارداد توسعه

| فایل | مسئولیت |
|---|---|
| [`inc/woocommerce/inquiries.php`](../inc/woocommerce/inquiries.php) | تنظیمات، نمایش، API، schema، rate limit، صف کارکنان، حفاظت خرید |
| [`assets/js/pages/woocommerce-inquiry.js`](../assets/js/pages/woocommerce-inquiry.js) | modal، نشست، ارسال، انتخاب متغیر بومی |
| [`assets/scss/pages/woocommerce-inquiry.scss`](../assets/scss/pages/woocommerce-inquiry.scss) | ورودی Sass |
| [`assets/scss/components/woocommerce/_inquiry.scss`](../assets/scss/components/woocommerce/_inquiry.scss) | سبک cream/green فرم و trigger |
| [`assets/css/pages/woocommerce-inquiry.css`](../assets/css/pages/woocommerce-inquiry.css) | خروجی کامپایل‌شده |
| [`tools/test-inquiries.php`](../tools/test-inquiries.php) | آزمون backend با fixture مستقل |
| [`tools/test-inquiries-browser.cjs`](../tools/test-inquiries-browser.cjs) | آزمون modal، responsive و swatch واقعی در مرورگر |

فقط `inquiries` به فهرست includeهای `inc/woocommerce.php` اضافه می‌شود؛ فایل خودش hookها را
ثبت می‌کند و hook تکراری نیاز نیست. key `woocommerce-inquiry` از فیلتر موجود `cn/page-keys`
اضافه و با لودر مرکزی قالب اجرا می‌شود. jQuery فقط برای رویدادهای بومی Woo/Swatches وابسته است؛
UI و شبکهٔ فرم JavaScript ساده هستند. ماژول `inc/Modules` یا class framework ندارد.

`voiceweb_wc_product_is_inquiry($product)` برای تصمیم مشترک کارت/صفحه است.
`voiceweb_wc_inquiry_button($product, $class='')` markup امن CTA را برمی‌گرداند؛ محصول متغیر
در کاتالوگ به صفحهٔ انتخاب گزینه لینک می‌دهد و ساده trigger مودال می‌سازد.

## اعتبارسنجی

```powershell
php -l wp-content/themes/voiceweb/inc/woocommerce/inquiries.php
node --check wp-content/themes/voiceweb/assets/js/pages/woocommerce-inquiry.js
php -d mysqli.default_port=10046 wp-content/themes/voiceweb/tools/test-inquiries.php
# با همان متغیرهای Playwright/PHP/مرورگر راهنمای RUNBOOK:
$env:VOICEWEB_WC_MYSQL_PORT='10046'
node wp-content/themes/voiceweb/tools/test-inquiries-browser.cjs
```

آزمون backend در این نوبت **۳۴ بررسی موفق** داشت: precedence تنظیمات، نرمال‌سازی موبایل،
origin/CSRF/proof، مهمان و مشتری، حریم خصوصی پاسخ، ثبت snapshot variation، موجودی/انتشار،
عدم سفارش و تغییر موجودی، مسدودسازی کلاسیک/Store API و شمارندهٔ پایدار.
fixtureهای مشتری/محصول/lead/counter در `finally` حذف و حالت خرید اولیه برگردانده می‌شوند.
mail و HTTP بیرونی در تست مسدودند. روی staging/local اجرا شود؛ تست fixture واقعی دیتابیس
می‌سازد و به اجرای همزمان چند نسخهٔ آن در production نیاز نیست.

آزمون Edge نیز **موفق** بود: باز/بستن و بازگشت فوکوس، Escape و keyboard trap بومی، عرض‌های
۳۲۰/۳۹۰/۷۶۸ بدون overflow، ثبت خصوصی درخواست مشتری، انتخاب swatch واقعی و reset متغیر،
نبود دکمهٔ خرید در فرم inquiry، بدون JavaScript error. تست مرورگر از یک مشتری موقت دارای
`manage_woocommerce` برای عبور از Coming soon بومی استفاده می‌کند. شمارهٔ fixture پیامک
نمی‌گیرد. MU guard موقت فقط IP همان fixture را برای شمارنده‌ها جدا می‌کند؛ در `finally`
محصول، مشتری، درخواست، شمارنده‌های fixture و guard حذف می‌شوند. تنظیم واقعی حالت خرید یا
Coming soon در این تست تغییر نمی‌کند. screenshot اختیاری از فرم **پیش از نوشتن موبایل** است.
